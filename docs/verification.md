# Build and verification

Use JDK 21. On Windows, use `gradlew.bat`; elsewhere, use `./gradlew`.
Generated bytecode targets Java 17. Module Gradle configuration determines Android debug
targets and device requirements. Run the following commands from the repository root.

## Common commands

```powershell
# SDK and default UI contracts
.\gradlew.bat :plugins:api:allTests :plugins:default-ui-api:allTests

# All configured multiplatform tests
.\gradlew.bat allTests

# Desktop runtime composition, real JAR loading, and UI rendering
.\gradlew.bat :plugins:platform-desktop:test

# Build both applications
.\gradlew.bat :apps:desktopApp:compileKotlin :apps:androidApp:assembleDebug

# Run desktop or install Android debug
.\gradlew.bat :apps:desktopApp:run
.\gradlew.bat :apps:androidApp:installDebug
```

`allTests` does not include every Android device instrumentation test, paid service calls,
actual Shizuku authorization, or root environment verification. Start with tests for the
changed module. Expand the scope when new failures, interface effects, or unresolved issues
justify it.

## Android instrumentation

```powershell
adb devices

# Platform plugin composition and real APK loading
.\gradlew.bat :plugins:platform-android:connectedDebugAndroidTest

# Host ADB settings broadcasts: models/credentials and provider replacement/revocation
.\gradlew.bat :apps:androidApp:connectedDebugAndroidTest `
  '-Pandroid.testInstrumentationRunnerArguments.class=ai.meteor.kcode.AdbSettingsPluginTest'

# Shared contracts and private implementations in a separate settings-command APK
.\gradlew.bat :plugins:platform-android:connectedDebugAndroidTest `
  '-Pandroid.testInstrumentationRunnerArguments.class=ai.meteor.kcode.plugin.AndroidSettingsCommandsApkTest'
```

Filters must match the corresponding test APK. Missing classes or zero executed tests do
not count as successful verification. Tests involving windows, dialogs, system overlays,
or input require an unlocked device and the appropriate system permissions. Instrumentation
installs test packages and may uninstall the target application. Run it on a test device
and never put real credentials in fixtures. Restore the ordinary application with
`:apps:androidApp:installDebug`.

## Acceptance criteria

| Boundary | Observable behavior |
| --- | --- |
| Dependencies and composition | Missing providers remain Pending; recovery rebinds consumers; invalid configuration is rejected during candidate preparation. |
| Dynamic package identity | Real JARs/APKs share SDK types; the host does not load private implementations; missing private dependencies have no fallback. |
| Revocation and cleanup | In-flight calls are cancelled and finalizers awaited; stale handles reject calls; repeated disposers preserve newer registrations. |
| Failed replacement | Committed UI, configuration, and installation manifests are preserved; candidate resources are released; mixed generations are never published. |
| Durable commits | Failed saves do not report success; multi-table transactions and schema migrations are explicit; restart recovery works. |
| UI | Actual rendering and semantics are observable; unloading removes components/effects; replacing dependencies preserves correct composition identity. |
| Native processes and windows | Exit/close and file release are verifiable; actual UIDs are checked; EPERM is not interpreted as process disappearance. |

Static scans, module counts, compilation, and one cold start provide supporting evidence;
they do not replace these behavioral assertions. Lifecycle tests using fake stores/clients
do not establish guarantees about actual networks or system permissions.

## Privileged verification

The native plugin's UID-2000 test entry point is
[PrivilegedDeploymentVerificationMain](../plugins/platform-android/src/androidTest/kotlin/ai/meteor/kcode/plugin/PrivilegedDeploymentVerificationMain.kt).
It requires the actual shell UID and runs through `app_process`, not ordinary app-UID
instrumentation. The driver checks package identity, command revocation, and deployment
resource cleanup. Its source code is authoritative for deployment parameters. See
[native-execution](../plugins/native-execution/README.md) for execution capabilities and
resource ownership.

## Scope of evidence

Record app-UID tests, UID-2000 `app_process`, cross-process BinderProxy calls, actual Shizuku
authorization, and UID-0 execution separately. Actual Shizuku authorization/connection and
root environment tests remain incomplete. Passing tests at other privilege levels does
not change that conclusion.

See [feature ownership](plugin-feature-audit.md) for current implementation and test locations.
When recording results, include the code revision, commands, tests actually executed, and
environment limitations. Old test counts or installation state do not establish acceptance
of the current version.
